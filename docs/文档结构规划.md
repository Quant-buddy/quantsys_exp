## 1. 结论

当前 `docs/第1个月/第1周/` 的结构适合项目启动，但不适合长期沉淀。因为第 1 周目录里同时放了三类文档：

```text
项目管理文档：任务清单、任务分配、岗位任务卡、验收清单
长期技术规范：run_id 规则、任务命令格式、数据落地方式
岗位交付文档：数据源探查、数据交接、问题清单
```

如果后续继续把所有文档都塞进“第几个月/第几周/岗位”，第 2 周以后会越来越难找长期规范。更合适的方式是：

```text
长期资产按领域放。
过程记录按时间放。
岗位产物先按周交付，稳定后沉淀到领域目录。
```

## 4. 为什么这样分

### 4.1 不是纯按时间

纯按时间会变成：

```text
02_技术规范/run_id规则.md
第1个月/第2周/技术负责人/run_id规则修订.md
第2个月/第1周/技术负责人/run_id规则再修订.md
```

后期新人不知道以哪个为准。

### 4.2 不是纯按岗位

纯按岗位会造成交接困难。比如 `fact_daily_bar` 是数据工程师生成的，但量化研究、策略研发、组合风控都会使用它。数据字典和质量规则不应该只属于数据工程师个人目录。

### 4.3 采用领域 + 时间

长期有效的内容放到领域目录，例如：

```text
02_技术规范/run_id规则.md
03_数据/数据字典/fact_daily_bar.md
04_研究/因子定义/ret_20d.md
07_组合风控交易/风控规则/涨跌停规则.md
```

阶段性过程记录保留时间目录，例如：

```text
01_项目管理/01_项目管理/第1个月/第1周/周五验收清单.md
03_数据/交付记录/第1周/data_issue_list.md
```

## 8. 判断文档放哪里的规则

新增文档时，先问三个问题：

1. 这个文档以后每周都会被复用吗？
   - 是：放领域目录。
   - 否：放项目管理或交付记录。
2. 这个文档描述的是业务/技术规则，还是某次会议/某周结果？
   - 规则：放领域目录。
   - 过程：按月份/周归档。
3. 这个文档会被多个岗位共同使用吗？
   - 是：不要放在某个岗位个人目录，放领域公共目录。
