# 周五验收清单

版本：v1.0  
日期：2026-07-07  
适用阶段：第一个月 MVP 冲刺第 1 周周五验收  

---

## 1. 验收目的

周五验收不是为了证明系统已经完成，而是为了确认：

```text
第 1 周的产物是否能接起来
主链路是否已经出现雏形
哪些问题会阻塞第 2 周
哪些需求应该延期
```

第 1 周周五的验收重点是：

```text
数据 -> 因子 -> 标签 -> 排名 -> 组合 -> 风控 -> 计划单
```

哪怕每一步都很粗糙，也要真实跑一遍。

---

## 2. 验收会议安排

建议时长：90-120 分钟

参会人员：

```text
技术负责人
数据工程师
量化研究员
基本面/事件研究员
策略研发工程师
组合风控/交易运维
出资人可旁听，但不建议在会议中临时加需求
```

会议顺序：

```text
1. 技术负责人说明验收目标。
2. 数据工程师演示数据样例和质检报告。
3. 策略研发工程师演示因子、标签和排名。
4. 量化研究员检查因子和标签合理性。
5. 基本面/事件研究员说明财务和行业可用性。
6. 组合风控演示组合、风控和计划单。
7. 技术负责人检查主链路、run_id、字段和问题清单。
8. 全员确认第 2 周任务。
```

## 4. 验收流程

## 步骤 1：检查工程骨架

负责人：技术负责人

检查项：

```text
项目目录是否建立
configs 是否存在
jobs 是否存在
sql/ddl 是否存在
docs 或 runbooks 是否存在
核心表名是否确定
命令行任务入口是否命名
run_id 规则是否有草案
```

通过标准：

```text
团队知道代码、配置、SQL、文档分别放哪里
```

不通过表现：

```text
每个人文件随意放
字段命名各用各的
没有统一任务入口
```

---

## 步骤 2：检查数据样例

负责人：数据工程师

检查项：

```text
是否能获取股票列表
是否能获取交易日历
是否有 20-50 只股票最近 3 年日线
是否有至少 1 个指数日线
是否有 open/high/low/close/volume/amount 字段
是否有 source 字段
是否有 update_time 或 run_id
```

最低通过标准：

```text
20 只以上股票
最近 3 年日线
能被策略研发读取
```

理想通过标准：

```text
50 只以上股票
数据落地到统一数据库或 Parquet
字段名已经统一
带 source 和 run_id
```

常见问题：

```text
股票代码格式不统一
日期类型不统一
成交额单位不统一
复权口径不清楚
AKShare 和 pytdx 字段含义不一致
```

---

## 步骤 3：检查数据质量报告

负责人：数据工程师

检查项：

```text
是否统计股票数量
是否统计交易日数量
是否统计日线覆盖率
是否检查 OHLC 合法性
是否检查成交量成交额非负
是否检查缺失值
是否列出异常股票和异常日期
```

最低通过标准：

```text
有一份 quality_report_v0.1
能说明哪些数据缺失或异常
```

理想通过标准：

```text
数据质量报告可重复运行
异常可以落表或导出 CSV
核心数据失败时能给出阻断建议
```

---

## 步骤 4：检查股票状态

负责人：数据工程师、组合风控/交易运维

检查项：

```text
是否能识别停牌
是否能识别涨停
是否能识别跌停
是否能识别上市天数
是否计划识别 ST
```

最低通过标准：

```text
样例数据中能判断停牌、涨停、跌停
```

理想通过标准：

```text
fact_stock_status 已有样例数据
组合风控可以直接使用状态字段
```

---

## 步骤 5：检查因子定义

负责人：量化研究员

检查项：

```text
本周落地因子是否明确
每个因子是否有公式
每个因子是否有输入字段
每个因子是否有窗口期
每个因子是否说明缺失处理
每个因子是否说明是否需要复权价格
```

本周建议验收因子：

```text
ret_20d
ret_60d
ma_gap_20d
volatility_20d
amount_ma_20d
```

最低通过标准：

```text
至少 3 个因子定义清楚
```

理想通过标准：

```text
至少 5 个因子定义清楚，并且代码已经生成结果
```

---

## 步骤 6：检查因子计算结果

负责人：策略研发工程师、量化研究员

检查项：

```text
因子结果是否包含 symbol
因子结果是否包含 trade_date
因子结果是否包含 factor_name
因子结果是否包含 factor_value
因子结果是否包含 run_id
因子值是否看起来合理
是否有大量 NaN
是否有异常极端值
```

最低通过标准：

```text
至少 3 个因子能对样例股票生成结果
```

理想通过标准：

```text
至少 5 个因子能生成结果
结果格式可以直接进入排名模块
```

---

## 步骤 7：检查标签定义和样例

负责人：量化研究员、策略研发工程师

检查项：

```text
是否定义 forward_return_10d
是否定义 forward_return_20d
是否从 T+1 开始计算
是否避免使用 T 日不可成交价格
标签是否包含 symbol、trade_date、horizon、forward_return
```

最低通过标准：

```text
标签定义清楚
有少量样例输出
```

理想通过标准：

```text
10日和20日标签都能批量生成
```

---

## 步骤 8：检查综合打分和排名

负责人：量化研究员、策略研发工程师

检查项：

```text
是否有 score 公式
是否能对样例股票排序
是否能解释排名靠前股票的原因
是否能排除明显不可交易股票
```

最低通过标准：

```text
能生成样例股票排名
```

理想通过标准：

```text
排名结果包含 alpha_score、rank_num、主要原因
```

---

## 步骤 9：检查行业和基本面样例

负责人：基本面/事件研究员

检查项：

```text
是否能获得行业分类
样例股票是否能匹配行业
财务字段是否有可用样例
财务字段是否有 publish_date 或可得日期
是否明确事件数据暂缓
```

最低通过标准：

```text
行业分类有样例
财务字段可得性说清楚
事件数据不阻塞主链路
```

理想通过标准：

```text
行业字段可以直接被组合模块使用
财务字段有明确防未来函数方案
```

---

## 步骤 10：检查目标组合

负责人：组合风控/交易运维

检查项：

```text
是否能从排名生成 TopN
是否能生成 target_weight
是否有单票上限
是否有现金保留
是否能处理不足 N 只股票情况
```

最低通过标准：

```text
能生成一个 TopN 等权组合样例
```

理想通过标准：

```text
组合结果包含 portfolio_id、trade_date、symbol、target_weight、reason、run_id
```

---

## 步骤 11：检查风控过滤

负责人：组合风控/交易运维、数据工程师

检查项：

```text
ST 是否禁止买入
停牌是否禁止交易
涨停是否禁止买入
跌停是否禁止卖出
上市不足 120 日是否禁止买入
低成交额是否禁止买入
是否有 risk_check_status
是否有 risk_block_reason
```

最低通过标准：

```text
风控规则文档清楚
计划单样例中有风控状态字段
```

理想通过标准：

```text
能自动生成 risk_check_report
每只被拦截股票都有原因
```

---

## 步骤 12：检查计划单

负责人：组合风控/交易运维、技术负责人

检查项：

```text
是否能输出 CSV 或 Excel
是否包含 trade_date
是否包含 account_id
是否包含 symbol
是否包含 stock_name
是否包含 side
是否包含 target_qty
是否包含 limit_price 或参考价格
是否包含 target_weight
是否包含 estimated_amount
是否包含 order_reason
是否包含 risk_check_status
是否包含 risk_block_reason
是否包含 approved_by
是否包含 run_id
```

最低通过标准：

```text
有 order_plan_sample_v0.1.csv
字段基本齐全
```

理想通过标准：

```text
计划单可以由目标组合和风控结果自动生成
```

```text

2 分：可运行、可检查、可进入下一周
```

## 6. 一票否决项

以下任意一项出现，视为第 1 周验收未通过：

```text
没有任何可读取的日线数据
没有统一字段格式
没有任何因子结果
没有计划单字段模板

团队仍在讨论大量第一个月不做的内容
```

## 8. 周五验收结论格式

验收结束时，技术负责人必须给出明确结论。

可以使用以下三种结论之一：

```text
通过：进入第 2 周，开始扩展全市场 3 年日线和数据质量。

有条件通过：进入第 2 周，但前 2 天必须补齐某些阻塞项。

不通过：暂停扩展，继续补第 1 周基础链路。
```

不要给模糊结论，例如：

```text
大家继续努力
整体还可以
后面再看
```

## 9. 第 2 周进入条件

只有满足以下条件，才建议进入第 2 周：

```text
1. 已有样例日线数据。
2. 已有 3-5 个因子结果。
3. 已有标签定义或样例。
4. 已有股票排名样例。
5. 已有计划单模板。
6. 已有数据问题清单。
7. 已有第 2 周任务清单。
```

如果不满足，优先补齐第 1 周主链路，不要急着扩展数据规模。

## 10. 与架构图和 MVP 冲刺书的一致性检查

周五验收时，技术负责人要额外检查以下一致性问题，防止第 1 周执行偏离系统总方向。

### 10.1 策略方向是否一致

检查：

```text
是否仍然坚持不做日内
是否仍然坚持不做高频
是否仍然以日频波段为主
是否仍然围绕看长做短、高抛低吸
```

如果发现团队开始讨论分钟线、盘口、Level-2、日内择时，应放入 backlog，不进入第一个月主链路。

### 10.2 数据边界是否一致

检查：

```text
是否只依赖 AKShare、pytdx、交易所/巨潮等免费公开数据
是否没有把收费数据设计成必需项
是否没有把北向、龙虎榜、资金流等不稳定数据设计成主链路必需项
```

### 10.3 系统主链路是否一致

检查：

```text
是否仍然围绕 数据 -> 因子 -> 标签 -> 回测 -> 组合 -> 风控 -> 计划单
是否没有绕过数据质量检查直接生成计划单
是否没有出现 notebook 替代生产任务的情况
```

### 10.4 风控原则是否一致

检查：

```text
数据质检失败是否阻断计划单
ST、停牌、涨停、跌停是否进入风控规则
计划单是否有风控状态和拦截原因
异常情况下是否默认不交易
```

### 10.5 复现原则是否一致

检查：

```text
关键产物是否有 run_id
配置是否没有硬编码
计划单是否能反查数据、因子、排名、组合和风控
```

## 11. 周五现场演示建议

周五验收最好不要只讲 PPT 或文档，建议现场按步骤演示。

最低演示链路：

```text
1. 展示样例股票池。
2. 展示一只股票的日线数据。
3. 展示数据质量报告。
4. 展示该股票某天的 3-5 个因子。
5. 展示标签样例。
6. 展示样例日的股票排名。
7. 展示 TopN 目标组合。
8. 展示风控拦截结果。
9. 展示 order_plan_sample.csv。
10. 用 run_id 反查其中一只股票的生成过程。
```

建议技术负责人随机抽查一只股票，问清楚：

```text
为什么它有这个分数？
为什么它进了或没进组合？
有没有被风控拦截？
计划单里的数量怎么算出来？
如果数据异常，系统会不会停止？
```

## 12. 周五验收后的动作

验收结束后，不要只宣布“通过”或“不通过”，必须形成后续动作。

验收后 24 小时内完成：

```text
1. 发布 week1_acceptance_report.md。
2. 发布 week2_task_plan.md。
3. 更新 data_issue_list.md。
4. 更新 factor_issue_list.md。
5. 更新 risk_issue_list.md。
6. 更新 backlog_optional.md。
7. 明确第 2 周每日目标。
```

如果结论是“有条件通过”，必须明确：

```text
哪些条件必须在第 2 周前 2 天补齐
谁负责
何时验收
补不齐是否暂停扩展全市场数据
```

---

## 13. 出资人旁听建议

出资人可以旁听周五验收，但建议只看三件事：

```text
1. 主链路有没有跑起来。
2. 风控和异常处理是不是清楚。
3. 下周任务是不是明确。
```

不建议在第 1 周验收会上临时追加：

```text
收益率目标
复杂模型要求
自动交易要求
更多数据源要求
```

这些可以进入 backlog，由技术负责人统一评估是否影响 MVP。
