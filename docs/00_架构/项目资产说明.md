# 项目资产说明

版本：v0.1
范围：当前仓库内代码文件、文档文件、配置文件、SQL 文件和第 1 周数据工程交付数据。

## 1. 这份文件的用途

这份文件是项目的轻量资产目录，用来回答三个问题：这个文件是什么，给谁用，怎么追溯是谁生成的。

当前项目还没有建立数据库，所以第 1 周数据工程产物先以 CSV、Markdown 和 `data/week1/manifest.json` 交付。等数据库链路确定后，建议把这里的数据文件清单升级为数据字典、数据血缘表和运行元数据表，而不是只靠聊天记录或个人记忆。

## 5. 数据文件

### 5.1 数据血缘结论

第 1 周 `data/week1/` 下的 CSV 文件，业务上应视为“数据工程师第 1 周交付物”。从代码证据看，它们由以下命令生成：

```bash
python jobs/week1_data_engineer_run.py --start-date 2023-01-01 --end-date 2026-07-07
```

当前 CSV 中的共同追踪字段包括：

```text
source：数据来源或派生来源
run_id：运行批次，例如 week1_data_engineer_20260707_20260707T140842
update_time：生成或更新时间
```

如果要弄清楚某个数据文件是谁生成的，建议按这个顺序查：

1. 先看 CSV 内的 `run_id`、`source`、`update_time`。
2. 再看 `docs/03_数据/交付记录/第1周/data_handoff_notes.md` 和 `data_issue_list.md`。
3. 再看生成入口 `jobs/week1_data_engineer_run.py` 中的 `_write_csv(...)` 调用。
4. 最后查 Git 提交记录、任务分配表、团队运行日志或聊天记录，确认实际执行人。

当前仓库可以确认“角色上是数据工程师生成，脚本上是 `jobs/week1_data_engineer_run.py` 生成”。复跑时应通过 `--operator` 传入自然人姓名或账号，并写入 `data/week1/manifest.json`；历史运行如果没有 operator，只能从 Git/沟通记录中查证。

## 6. 推荐的长期做法

### 6.1 现在应该写 Markdown 吗？

应该写，而且本文件就是第一版。原因是项目还小、数据库未建、团队成员只有 6 人，Markdown 成本最低，最适合把文件作用、字段口径、责任人和复跑命令先固化下来。

但不要长期只靠一个 Markdown。Markdown 适合做人读的说明，不适合机器自动校验，也不适合准确回答“某一次运行到底生成了哪些文件、输入是什么、代码版本是什么、执行人是谁”。

### 6.2 更推荐的办法

当前已经新增机器可读的运行清单，后续每次复跑都应保留 Markdown，同时更新：

```text
data/week1/manifest.json
```

每次运行记录这些字段：

```json
{
  "run_id": "week1_data_engineer_20260707_20260707T140842",
  "task": "week1_data_engineer",
  "operator": "数据工程师姓名或账号",
  "command": "python jobs/week1_data_engineer_run.py --start-date 2023-01-01 --end-date 2026-07-07",
  "git_commit": "当前提交哈希",
  "started_at": "2026-07-07T14:08:42",
  "ended_at": "2026-07-07T14:09:05",
  "outputs": [
    {
      "path": "data/week1/clean/fact_daily_bar.csv",
      "rows": 25402,
      "source": "akshare.stock_zh_a_daily.qfq",
      "schema_version": "v0.1"
    }
  ]
}
```

等数据库建好后，再把同样的信息落到元数据表，例如：

```text
meta_run
meta_dataset
meta_dataset_version
meta_data_lineage
meta_quality_check
```

### 6.3 真实业务场景中会有人这么做吗？

会，而且成熟团队一定会做，只是形式不同。

小团队早期通常用 README、数据字典、交接文档、运行日志和 issue 清单。中大型量化团队会进一步使用数据目录、元数据表、任务调度系统日志、数据血缘平台、质量监控和权限审计。原因很现实：量化系统最怕数据来源不清、口径变了没人知道、某次回测无法复现、实盘出错后查不清是哪批数据导致的。

对你们当前阶段，最合适的强度是：

1. 保留 `docs/00_架构/项目资产说明.md` 作为人读入口。
2. 每个数据脚本都必须写 `run_id`、`source`、`update_time`。
3. 数据运行脚本已经生成 `manifest.json`，后续继续补充输入文件、依赖版本和质量检查摘要。
4. 建库后把 manifest 信息迁移到元数据表。
5. 每个 CSV 或数据库表都要有字段字典、生成脚本、负责人、更新频率和质量检查规则。
